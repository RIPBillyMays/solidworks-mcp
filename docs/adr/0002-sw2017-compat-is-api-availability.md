# ADR-0002: SOLIDWORKS 2017 compatibility is an API-availability problem, not a ProgID/registry problem

- **Status:** Accepted (evidence gathered 2026-10-08)
- **Date:** 2026-10-08

## Context
The advice that started this project was to "modify the version checking logic and registry hooks to target `SldWorks.Application.25`". On this machine:

- `HKCR\SldWorks.Application` and `HKCR\SldWorks.Application.25` both resolve to CLSID `{6B36082E-677B-49E8-BCB2-76698EBD2906}`. SOLIDWORKS 2017 SP05 (25.150.83) is the only installed version.
- The chosen server has **no version gate**. It calls `GetActiveObject("SldWorks.Application")`.
- The real risk is calling API members that were added after 2017. SOLIDWORKS never changes a published method's signature. New behavior ships as a numbered variant (`SaveAs` → `SaveAs2` → `SaveAs3`). So whether a call works on 2017 comes down to whether its name exists in the 2017 type library.
- The sldworks typelib `{83A33D31-27C5-11CE-BFD4-00400513BB57}` is registered under key `19.0`. **That key is hex** (0x19 = 25), so `LoadRegTypeLib(guid, 19, 0)` fails with "Library not registered".

## Decision
1. **No registry changes.** Keep the version-independent ProgID.
2. **Commit a 2017 API snapshot:** `tools/compat/sw2017_api_members.txt` (21,007 `Interface.Member` lines from sldworks + swconst, generated by `tools/compat/dump_sw_tlb.py`). Because it's committed, the compat test runs offline and in CI without SOLIDWORKS.
3. **Phase 2 adds `tests/test_sw2017_api_compat.py`.** It fails if any SW member referenced by `solidworks_mcp/` (attribute calls plus the name tuples passed to `flag_methods`) is missing from the snapshot. Non-SW names go in an allowlist, each with a reason.
4. **Extend the snapshot with enum values** (e.g. `swEndConditions_e.swEndCondBlind=0`) so the hard-coded constants in `sw_core.py` can be checked too.
5. **Optional pin (Phase 7):** a `SW_PROGID` environment variable, defaulting to `SldWorks.Application`. It only matters if a second SOLIDWORKS version is ever installed side by side.

## Consequences
- A static pass doesn't guarantee runtime behavior. 2017 bugs, silent `None` returns, different feature type-name strings and dialog behavior can only be found live (Phase 3).
- Upstream merges are gated by the compat test, so a post-2017 call can't slip in unnoticed.
- The snapshot is specific to SW 2017 SP05. Regenerate it if SOLIDWORKS is upgraded, and then revisit this ADR.

## Alternatives considered
- **Pin `SldWorks.Application.25` everywhere now.** No benefit with one installed version, and it would add a fork diff in several places.
- **Early binding via `gencache.EnsureModule` on the 2017 typelib.** Fixes some marshalling, but upstream is built and tested on late binding, so it would be a large behavioral change. Revisit only if late-binding issues dominate Phase 4.
